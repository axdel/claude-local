How the claude-local loop works

A deterministic red → green loop that drives a free local model to write code — and can never be talked into declaring itself done.

1The shape of it: three actors, one barrier

claude-local is a loop, not an agent. Nobody hands a chat model a repo and hopes. Instead, three parties each do exactly one job, and the boundaries between them are the whole design.

  • The frontier orchestrator (a strong model, e.g. this one) writes the task spec, writes a failing test that is the sole definition of “done”, and sets the budget. It never writes the implementation.
  • The loop (plain Python, no intelligence) hands the model a prompt, applies whatever text comes back to one permitted file, runs the test, and decides. It is the only actor allowed to call the run “done”.
  • The local model (a small, free, often weak model) receives the prompt and returns one complete file as raw text. No tools, no shell, no file access — and crucially, it never receives a test it can edit.

The single load-bearing idea: the test is the oracle, and the model can never touch it. A weak model cannot “win” by deleting an assertion, importing the test away, or claiming success — because it never holds the test, and only a genuinely green run ends the loop.

2The four things the loop moves around

Everything the loop needs for one task is a small, immutable TaskSpec:

  • impl_path — the one file the model is allowed to write (e.g. src/calculator.py).
  • spec_text — the plain-English description of what to build.
  • test_text — the immutable oracle test. The loop writes it to the worktree root, on purpose: that puts it outside the model’s writable folder and outside any snapshot, so it can never be overwritten.
  • budget — three hard caps: max_attempts (how many tries), max_tokens (how long each decode may run), timeout_s (wall-clock). All strictly positive.

3One turn of the loop, step by step

The loop builds the prompt’s stable front once, writes the oracle test once, then repeats a tight cycle until the test passes or the budget runs out.

In order, each attempt does exactly this:

  • Generate. Send the stable prefix plus (after the first try) a distilled feedback tail. Stream the tokens back.
  • Guard the decode. If the derail guard trips mid-stream (see §6), abort and stop — this run is DERAILED.
  • Extract the whole file. Pull the complete file block out of the raw text. If the model returned only prose with no usable block, stop — BLOCKED.
  • Apply it — to one path only. Write it to impl_path. If the extracted edit aims anywhere else, the path guard refuses it and the run stops — BLOCKED.
  • Run the oracle. Execute the frozen test in a subprocess and read a structured score.
  • Snapshot. Capture the attempt and its score (see §5).
  • Decide. Green → break, we’re DONE. Otherwise loop again with the failure as feedback.

The score is never scraped from console text — the loop runs uv run pytest with a JUnit-XML report and parses that. A run counts as green only when exactly the expected number of tests ran and all passed. That count-pin is what stops a model from “passing” by making the tests disappear: skip one, import it away, or break collection, and the count falls short — invalid, not green.

4A worked example: teaching a model to add

The spec asks for add(a, b). The orchestrator’s oracle pins three sums it worked out by hand — never by running any code:

from calculator import add

def test_add_two_positives():  assert add(2, 3)   == 5
def test_add_with_zero():      assert add(7, 0)   == 7
def test_add_two_negatives():  assert add(-4, -6) == -10

Now watch a weak model fumble toward the answer. It cannot see these are the assertions’ reasons — it only ever gets told how many passed and which failed.

  • Attempt 1 — abs(a) + abs(b). Passes the two non-negative cases, fails the negatives (it returns +10, not −10). Score: 2/3. The failure — the failing test’s name and a slice of the traceback — becomes the feedback for the next try.
  • Attempt 2 — a - b. The model over-corrects and regresses to 1/3. This is the exact trap the loop is built to survive: repair feedback can make things worse. The loop keeps attempt 1 as the best-so-far and moves on.
  • Attempt 3 — a + b. All three sums match. The run is green, the loop breaks, and the task is DONE.

5The safety net: never end worse than your best

Because a repair can regress (attempt 2 above), the loop treats every attempt as a candidate and keeps a snapshot of each. After the loop ends — for any reason — it restores the single best one it ever saw. “Best” is a strict ranking: most tests passed, then fewest crashes, then fewest failures, then earliest attempt to break a tie. A crashed attempt (zero passing) always ranks below any attempt that ran even one test.

So imagine the model never stumbles onto a + b and the budget runs out at 2/3 → 1/3 → 0/3. The loop doesn’t leave you with the last, worst attempt. It rewinds the file to the 2/3 version from attempt 1 and reports EXHAUSTED — the most-correct code it managed, not the most-recent.

This is why a green result is trustworthy and a non-green result is still useful: you always walk away holding the best implementation the model produced, byte-for-byte.

6Why the front of the prompt never changes

Local inference is bound by memory bandwidth, and the most expensive part of a call is re-reading a long prompt. Model servers cache that work — the prefill KV cache — but only for a prefix that is byte-for-byte identical to a previous call. So the loop makes the front of the prompt a hard invariant: the rules card, the spec, and the immutable test, in a fixed layout, with no timestamps, run ids, or absolute paths. Only the small feedback tail differs between tries.

The feedback tail is deliberately small — a one-line score, the failing test names, and the last lines of output, stripped of absolute paths and capped at 4 KB. Enough signal to fix the bug; too little to flood the decode or accidentally look like a repetition loop to the guard.

7The derail guard: bounded decode by construction

Small models get stuck — repeating a line forever, rambling past any useful length, or simply hanging. Waiting for a full completion to notice is wasted time and tokens. So the loop consumes the stream as it decodes and watches it with three trip-wires, checked on every chunk. The first to trip aborts the generation immediately.

  • Timeout — an injected wall clock passes the deadline. (Injected, so tests drive it deterministically.)
  • Token cap — decoded characters exceed max_tokens × 4, a lenient client-side backstop behind the server’s own hard token limit.
  • Repetition — a substantial line (≥ 24 chars) repeats 6 times in a row after a short warmup. Short lines like } or pass are transparent — they repeat harmlessly in real code. Detection rides a fixed deque(maxlen=6) ring buffer: when it’s full and every entry is identical, that is the trip — no growing scan, no accidental slowdown in the hot loop.

This bounds the decode. Bounding the test run the model’s code triggers — and every local-server failure mode around it — is a separate, ongoing hardening concern.

8How a run ends

Every run resolves to exactly one of four outcomes, chosen by strict precedence — a real green always wins, even if a later attempt then derailed:

  • DONE — a snapshot went green. Success, full stop.
  • DERAILED — a decode was cut by the guard and nothing ever passed.
  • BLOCKED — the model never produced a usable whole file for the permitted path (only prose, or an edit aimed elsewhere).
  • EXHAUSTED — the attempts ran out; the best partial was restored.

On every terminal outcome, the loop also emits its half of a per-task economy record — tokens spent, attempts used, wall-clock, outcome. That’s the point of the whole exercise: to measure, task class by task class, whether handing work to a free local model actually saved frontier tokens, rather than assuming it did.

9Design lineage — Aider, and the papers

An honest answer, because it was asked directly: no code, format, or algorithm here was copied from Aider or from any specific paper, and the repository cites none — the only external references in the tree are the OpenAI streaming-API docs and the mlx-lm server, used to get the wire format of the token stream right.

That said, this design lives in a well-explored neighbourhood, and it would be dishonest to claim the ideas are unprecedented. Several elements rhyme with established work — convergent solutions to shared problems, not borrowings:

  • Whole-file edits. Returning a complete file as text is the most robust edit format for a weak model — no diff to misalign, no line numbers to miscount. Aider is well known for making whole-file and diff edit formats a first-class concern; landing on whole-file for weak local models is the same reasoning reaching the same place.
  • An “architect vs editor” split. Separating the party that decides what’s correct from the party that writes the code is a pattern Aider also uses. Here the split is sharper and adversarial: the “architect” ships an immutable test the “editor” can never see or edit.
  • Test-failure feedback loops. Feeding failing test output back to a model is the backbone of many agentic coding systems. claude-local’s twist is that the test is the sole, count-pinned oracle and the model has no way to declare victory — only a green run can.

What is genuinely particular to this loop, and where its value concentrates:

  • an orchestrator-owned immutable oracle the model can neither edit nor import away, enforced by a pinned test count;
  • the best-passing snapshot — repair can regress freely, and you still keep the best result;
  • a derail guard shaped around the specific failure modes of small local models;
  • the byte-stable prefix treated as a hard invariant so the prefill cache is actually reused;
  • and per-task economy metering, so “offload it to a free model” is a measured claim, not a hope.
